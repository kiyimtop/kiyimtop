# ⚠️ Прочитай это ПЕРВЫМ — правила для любого ИИ (Claude и других), который работает с KiyimTop

Этот файл — для ИИ-помощника. Владелец проекта **не программист**: он загружает файлы на GitHub через сайт
и не может сам распутать «хаос». Раньше разные помощники переделывали проект каждый по-своему
(GitHub Pages, Vercel, Supabase, сервер с ключами…), и сайт по разным ссылкам показывал разное.
**Не повторяй этого.** Если какое-то правило ниже мешает задаче — сначала спроси владельца, не нарушай молча.

## 0. Перед работой
1. Прочитай **весь `CLAUDE.md`** — там подробное описание проекта, кода и правил.
2. Отвечай владельцу **на русском, простыми словами**, без жаргона.
3. **Одна задача за раз.** Большие переделки («переписать на другой фреймворк», «перенести на другой
   хостинг», «поменять базу») — только если владелец прямо попросил. Не предлагай их «заодно».

## 1. Архитектура зафиксирована (с 13.11.2026, «как в TheStarth») — не меняй её
| Что | Как сделано | Чего НЕ делать |
|---|---|---|
| Сайт | React + Vite, папка `src/` | Не переписывать на Next.js, Vue, чистый HTML и т.п. |
| Хостинг | **Только Cloudflare Workers** (`kiyimtop.kiyimtop.workers.dev`, позже `kiyimtop.uz`), сам собирается из GitHub | Не включать GitHub Pages, Vercel, Netlify, Firebase Hosting. Один сайт — один адрес |
| Код | **Только репозиторий GitHub `kiyimtop/kiyimtop`**, ветка `main` | Не создавать вторые ветки/репозитории «для теста» |
| База и вход | **Firebase** (Firestore + Authentication). Сайт сам читает и пишет в базу через `firebase` SDK | Не переносить на Supabase, MongoDB, свой сервер и т.п. |
| Безопасность | **Правила `firebase/firestore.rules`** решают, кто что может | Не переносить брони/кабинет/админку обратно на сервер с ключом |
| Сервер | `server/` (Cloudflare Worker) — **только Telegram-бот и фото** (`/api/photo`, `/api/notify`, бот) | Не добавлять туда логику сайта. Сайт должен работать даже без серверных ключей |

## 2. Как устроен код (куда что писать)
- Экраны (`src/pages`, `src/components`) **не обращаются к Firebase напрямую** — только через `src/lib/`:
  `fb.js` (подключение), `db.js` (помощники), `auth.js` (вход, профиль), `catalog.js` (каталог),
  `bookings.js` (брони), `seller.js` (кабинет магазина), `admin.js` (админ-панель), `notify.js` (бот).
- **Все надписи — в `src/locales/uz.json` и `src/locales/ru.json`, всегда в оба файла.** Узбекский — латиница.
- Цвета — только через переменные в `src/styles/global.css`. Дизайн не менять, если не просили.
- Даты из базы приходят текстом ISO (через `plain()` в `db.js`) — экраны рассчитывают на это.
- В Firestore **нельзя записывать `undefined`** (будет ошибка) — пустое значение = `null`.
- Запросы к базе — **только по одному полю** (`where`), чтобы не нужны были составные индексы.

## 3. Самое частое место поломок — правила базы
Каждый раз, когда добавляешь **новую коллекцию, новое поле или новое действие**:
1. Обнови `firebase/firestore.rules`. Во многих местах стоит список разрешённых полей
   (`hasOnly([...])`) — **новое поле нужно вписать туда**, иначе запись молча откажет («Нет доступа»).
2. Дай владельцу **весь текст правил** и скажи: Firebase → Firestore Database → Rules → вставить → **Publish**.
3. Не ломай служебные вещи:
   - у товара поля `hold_ref`, `hold_op`, `hold_idx` — проверка, что бронь забирает/возвращает ровно 1 штуку;
   - у брони `owner_uids` — копия владельцев магазина (по ней магазин видит свои брони);
   - поля `notified_*` пишет только сервер бота.
4. Роли: `users/<uid>.role` = `admin` | `moderator` | `seller` | пусто (покупатель).
   Первого админа владелец ставит руками в Firestore. Себе роль через сайт выдать нельзя — так и задумано.

## 4. Ключи и пароли
- Никогда не писать ключи и токены в код, README, комментарии или чат. Секреты — только в Cloudflare
  (Settings → Variables and Secrets), публичные `VITE_…` — в Cloudflare → Settings → Build → Variables.
- Если владелец прислал ключ в чат — предупреди и предложи заменить его.

## 5. Как отдавать работу владельцу (обязательно, каждый раз)
1. **Проверь**, что проект собирается (`npm run build`). Если собрать не можешь — честно скажи об этом.
2. Дай **архив только с изменёнными и новыми файлами**, с той же структурой папок, что в проекте
   (владелец загружает его на GitHub через Add file → Upload files, файлы заменяются поверх).
3. Напиши **списком**: какие файлы изменены, какие новые, и **какие файлы удалить вручную** на GitHub
   (загрузка ничего не удаляет; удалять — ⋯ → Delete file). Без необходимости файлы не удаляй и не переименовывай.
4. Если менялись правила — отдельно файл `firebase/firestore.rules` и шаг «вставить и Publish».
5. В конце — раздел **«Как проверить»**: что открыть, что нажать, что должно получиться.
6. Если поменял архитектуру или добавил важное — **обнови `CLAUDE.md` и этот файл**.

## 6. Чего не трогать без просьбы владельца
- Адреса страниц (`src/lib/router.jsx`), Telegram Mini App (`src/lib/platform.js`), PWA (`public/sw.js`, манифест).
- Витрину на главной (`src/components/Showcase.jsx`, `showcaseArt.js`) и фирменные цвета.
- Тексты для бота (`server/bot-texts.js`) — только вместе с обоими языками.

## 7. Если что-то «не работает»
Сначала проверь, а не переписывай:
- открыт ли правильный адрес (Cloudflare, а не старая копия на GitHub Pages);
- опубликованы ли последние правила Firebase (ошибка «Нет доступа» / `permission-denied` — почти всегда правила);
- включены ли в Firebase → Authentication способы входа и добавлен ли домен сайта в Authorized domains;
- есть ли у пользователя нужная роль в `users`.
Чини точечно, объясни владельцу причину простыми словами.
